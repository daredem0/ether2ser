# Interface Design Description

## Purpose

The management interface configures and observes one ether2ser device. USB CDC and HTTP expose the same resource catalog and execute requests through the same management core; only parsing and response rendering are transport-specific.

The management plane is separate from the synchronous V.24 data link. USB CDC is not a serial data bridge, and HTTP traffic is not carried through the bridge UDP socket.

## 1. USB CDC serial interface

### Transport

- USB CDC, line-oriented printable ASCII.
- Conventional terminal setting: 115200 baud, no flow control.
- Interactive commands are human-facing and produce formatted text without protocol markers.
- One interactive command per line; maximum length is 127 characters.

`tools/serial_console.py` remains the exclusive console owner when automation and human clients share a board. Its interactive `client` forwards normal human commands unchanged.

### Human command grammar

```text
help [resource]
status
mem
net
config
v24
mode [bridge|gpio]
pins
pininfo <signal>
get gpio <signal>
set gpio <signal> <0|1>
get net <setting>
set net <setting> <value>
get v24 <setting>
set v24 <setting> <value>
get loglevel
set loglevel <error|info|debug|trace>
save
wipe wipe
reboot
```

The short commands are primary. In particular, health is queried with `status`, not `get status`. `help` presents aligned command groups, valid values, examples, pins, and baudrates. `help <resource>` gives focused usage.

Examples:

```text
status
net
mode gpio
set gpio rts 1
mode bridge
set net ip.local 192.168.29.20/24
set net ip.remote 192.168.29.5
set v24 baudrate 16000
set v24 txclock internal
save
```

Status and configuration output use headings, aligned labels, units, and grouped counters. They intentionally do not expose REST paths such as `status.frames.udp_rx` as the human presentation.

### Automation framing

The broker's `send` operation prefixes commands with a reserved `@` byte. Only these automation requests receive response markers:

```text
@response 12 begin status
status: ok
Operating mode: bridge
...
@response 12 end ok
```

The prefix is generated by the broker and is not part of the human command language. It lets automation match a sequence and terminal result despite concurrent logs. The broker's interactive client does not add it. Framed automation commands are limited to 126 user bytes so the prefix remains within the firmware's 127-byte line limit.

Result names include `ok`, `accepted`, `not_found`, `read_only`, `invalid_value`, `conflict`, `busy`, `too_large`, and `internal_error`.

### Common resources

| Function | Human serial command |
|---|---|
| Runtime status | `status` |
| Memory usage | `mem` |
| Complete configuration | `config` |
| Network summary | `net` |
| Local/remote/gateway IP | `get|set net ip.local|ip.remote|ip.gateway ...` |
| Local/remote UDP port | `get|set net udp.port.local|udp.port.remote ...` |
| V.24 summary | `v24` |
| Baudrate | `get|set v24 baudrate ...` |
| TX clock | `get|set v24 txclock internal|external` |
| Signal inversion | `get|set v24 invert ...` |
| CTS restart | `get|set v24 ctsrestart on|off` |
| Log level | `get|set loglevel ...` |
| Bridge/GPIO mode | `mode [bridge|gpio]` |
| Pin catalog/detail | `pins`, `pininfo <signal>` |
| GPIO level | `get|set gpio <signal> ...` |

Known GPIO signal names are `txd`, `rxd`, `rts`, `cts`, `dtr`, `dsr`, `dcd`, `tx_active`, `tck`, `rck`, `xck`, and `w550_reset`.

### Mode and effect rules

- `bridge` mode owns the V.24 pins and rejects manual GPIO writes.
- `gpio` mode disables UDP/V.24 bridging. Only non-reserved output signals may be written.
- Mode and TX-clock changes require an idle data path, persist automatically, and reboot when changed.
- Network, baudrate and inversion changes persist automatically.
- CTS restart and log level are runtime-only until `save` is issued.
- `wipe wipe` is deliberately redundant confirmation; it erases persisted configuration and requires a reboot to use defaults.

## 2. HTTP REST API

### Transport and endpoint

- HTTP/1.1 over TCP port 80 on the configured W5500 IPv4 address.
- No separate REST address or port setting.
- W5500 socket 2 serves one bounded, nonblocking connection at a time.
- Every response is JSON and includes `Connection: close`.
- Maximum request size is 1024 bytes; maximum response size is 4096 bytes.
- Chunked transfer encoding is not supported.
- There is no authentication or TLS. The API is intended only for a trusted, isolated LAN.

### Resource mapping

The base path is `/api/v1`. Serial resource dots become URI slashes:

| Operation | HTTP request |
|---|---|
| Read a resource | `GET /api/v1/<resource/path>` |
| Set a resource | `PUT /api/v1/<resource/path>` with `{"value":...}` |
| Save configuration | `POST /api/v1/actions/save` with no body |
| Reboot | `POST /api/v1/actions/reboot` with no body |
| Wipe configuration | `POST /api/v1/actions/wipe` with `{"confirm":"wipe"}` |

Examples:

```http
GET /api/v1/status HTTP/1.1
Host: 192.168.29.20
```

```http
PUT /api/v1/system/mode HTTP/1.1
Content-Type: application/json
Content-Length: 16

{"value":"gpio"}
```

```http
PUT /api/v1/gpio/rts HTTP/1.1
Content-Type: application/json
Content-Length: 11

{"value":1}
```

Other direct mappings include `/api/v1/config`, `/api/v1/net/ip/local`, `/api/v1/v24/baudrate`, `/api/v1/pins`, and `/api/v1/gpio/cts`. Values use the same textual forms as the serial interface; JSON strings are required for values such as `internal`, `on`, and `debug`.

### Responses

A successful scalar response contains the canonical resource path and value:

```json
{"result":"ok","path":"system.mode","value":"bridge"}
```

Group resources return a structured object. For example, `GET /api/v1/status` returns the same runtime snapshot represented by the serial `status.*` lines.

Errors use a stable result name:

```json
{"result":"error","error":"conflict"}
```

| HTTP status | Meaning |
|---:|---|
| 200 | Request completed or value already matched |
| 202 | Disruptive effect accepted |
| 400 | Invalid syntax or value |
| 404 | Resource not found |
| 405 | Method not allowed or resource read-only |
| 409 | Current mode or active data path conflicts with the request |
| 413 | Request exceeds the fixed buffer |
| 503 | Resource is busy |
| 500 | Internal failure |

Effects that could disrupt their own HTTP response—such as changing the local IP, switching mode, or rebooting—are applied only after the response has been transmitted and the TCP connection has closed.
